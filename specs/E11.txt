title: 调试体制
summary: 找出并消灭 bug 的调试体制每款游戏都需要。流程：统一 ROM 版本 → 按规格书穷举、分区检查并建检查清单 → 复现后写成工单 → 管理者评级（S 卡死/存档损坏、A 阻碍进行）并分配 → 修复后回到调试员确认 → 完成状态保存。还有电脑自动测试、全球接力调试；而修 bug 可能引入新 bug。

tldr: 找出程序缺陷 bug 并消灭它的调试体制，是所有游戏都需要的。通常在产品版里浮出水面的只是极少数 bug，在那之前修了数不清的 bug。能修改游戏的员工（尤其是程序）若也去做测试游玩，时间损失很大，所以大多设立调试员等，有组织地找 bug，甚至有调试专门公司。樱井为难以想象实际体制的人大致讲解调试流程：<b>大前提是统一每天更新的 ROM 版本</b>——在不同版本上出的 bug 没有参考价值，很麻烦。首先测试游玩：不是漫无目的地玩，而是把规格书上写的项目组合逐一穷举，或分成小组细查负责部位，不放过遗漏；也会制作检查清单。发现 bug 后摸清复现方法，写成<b>工单（ticket）</b>报告——工单就是写在网络上的任务，确实交接能减少遗漏的可能。管理者按工单的重要性给 bug 评级：<b>S 级是卡死或可能损坏存档的，A 级是妨碍游戏进行的</b>等，级别低的视情况可能搁置。评级的同时决定分给哪个部门或负责人——bug 不一定只由程序修：角色贴图错乱由美术修，动作破绽由动作设计修。修正反映后工单回到调试员手里，在多种组合下确认修好了才终于结束；但工单不会删除，而是以「完成」状态保存，以防再发。通过工单在负责人间交接，不让它悬空、确实地交接修正。相关的 bug 工单之间会互相参照或合并；工单积压多的人，别人会接过一部分帮忙——任务可视化在任何事上都很重要。调试最难的游戏，首先是《大乱斗》这种；开放世界作品能无限移动也很难。这种情况只靠人手很辛苦，所以也会让电脑跑来找问题：《大乱斗》也会让电脑对战跑一整晚来找 bug。调试总之需要次数，到了后期会在全世界进行：日本、欧洲、美国接力同一份 ROM 数据推进。但 bug 最麻烦的是<b>修 bug 可能引入新 bug</b>，和 bug 本身一样，不是小心就能防住的。无论如何问题都会出现，为了迅速发现、迅速解决，世界各地现在也在进行调试。
# 为什么需要调试体制 | 为什么 | 3
p: 找出程序缺陷 bug 并消灭它的调试体制，所有游戏都需要。通常在产品版里浮出水面的 bug 只是极少数，在那之前已修正了数不清的 bug。
p: 能修改游戏的员工（尤其是程序）如果也去做测试游玩，时间损失很大。所以大多会设立调试员，有组织地找 bug——甚至有专门做调试的公司。

# 前提：统一 ROM 版本 | 统一版本 | 47
!: 首先的大前提：每天更新的 ROM 版本要统一。在不同版本上发现的 bug 没有参考价值，会很麻烦。

# 测试与检查清单 | 测试 | 55
p: 调试员进行测试游玩，但不是漫无目的地玩：把规格书上写的项目组合逐一穷举，或者分成小组、细查负责的部位，避免遗漏。也会制作检查清单。

# 工单与评级 | 工单 | 72
p: 发现 bug 后，先摸清复现方法，然后写成<b>工单（ticket）</b>报告。工单就是写在网上的任务；把任务确实交接下去，能减少遗漏的可能。
fig: 88 | 工单：写在网上并追踪的任务
p: 管理者根据工单的重要性给 bug 评级：<b>S 级</b>是卡死或可能损坏存档的；<b>A 级</b>是妨碍游戏进行的；级别低的视情况可能被搁置。
fig: 112 | Class S：卡死与崩溃；Class A：阻碍进行与冻结
p: 评级的同时，决定分配给哪个部门或负责人。bug 不一定只由程序来修：角色贴图错乱由美术修，动作破绽由动作设计师修。
fig: 122 | 不只是程序员修 bug

# 确认与保存 | 确认 | 128
p: 修正反映后，工单再回到调试员手里，在多种组合下确认修好了，才终于结束。
p: 但工单不会被删除，而是以「完成」状态保存，以防再次发生。
fig: 144 | 工单不丢弃，标为「已解决」
p: 通过在负责人之间传递工单，不让问题悬空，确实地交接和修正。相关的 bug 工单之间会互相参照或合并；工单积压太多的人，其他人会接过一部分帮忙。
fig: 168 | 相关 bug 的工单会被交叉参照或合并
!: 任务的可视化，在任何事上都很重要。
